# 微信网络观测技术文档

本文档说明如何从 Linux 主机侧观测微信进程的网络行为。这里的“微信技术文档”聚焦于 eBPF 网络追踪：识别微信进程、跟踪 TCP 连接建立、发送方向数据写入，以及把观测结果暴露给日志或 Prometheus。

本文不涉及微信协议解析、消息内容解密或业务数据抓取。观测程序只记录进程、线程、socket、地址、端口、连接状态、耗时、发送字节数等元数据。

## 目标场景

典型问题包括：

- 微信进程是否正在建立 TCP 连接。
- 微信连接建立耗时是否异常。
- 微信进程是否存在大量短连接、失败连接或重连。
- 微信发送方向是否有持续流量。
- 微信进程网络行为能否和 CPU off-cpu、调度切换数据一起分析。

适合的排查方式是：

```text
定位微信进程 -> 指定目标 PID -> 加载 eBPF 程序 -> 观察日志和 /metrics -> 对照网络连接状态
```

## 当前项目能力

当前仓库和网络观测相关的主要代码位置：

```text
user/src/loader/mod.rs              # 命令行参数和 eBPF 加载入口
user/src/loader/network.rs          # 网络 kprobe / tracepoint 加载逻辑
user/src/metrics/network.rs         # 网络指标采集和 Prometheus 输出
ebpf/src/network/tcp.rs             # TCP connect、sendmsg、连接状态追踪
ebpf/src/network/socket.rs          # socket、recvmsg、accept 等实验入口
common/src/lib.rs                   # 用户态/eBPF 共享结构体
```

当前已经具备的能力：

- 通过 `--target-pid PID` 配置目标进程 PID。
- 通过 `TARGET_PID` map 把目标 PID 写入 eBPF 侧。
- eBPF 侧可按目标 PID 过滤网络事件。
- `tcp_v4_connect` kprobe 可记录连接发起时刻。
- `sock:inet_sock_set_state` tracepoint 可观察 socket 状态变化。
- 当连接从 `SYN_SENT` 进入 `ESTABLISHED` 时，可以计算连接建立耗时。
- `tcp_sendmsg` kprobe 代码已经实现读取 TCP 四元组和发送字节数。

当前需要注意的限制：

- 示例加载逻辑目前只 attach 了 `tcp_v4_connect`，`tcp_sendmsg` 的 attach 配置还是注释状态。
- `sys_enter_connect` tracepoint 的加载配置目前也是注释状态，因此 `network_tcp_pid_total` 指标暂时不会随 connect 事件增长。
- 当前过滤条件是单个目标 PID，不会自动覆盖微信子进程或多进程实例。
- 当前代码主要覆盖 IPv4 connect 耗时；IPv6、UDP、DNS、TLS 层内容不在当前能力范围内。

## 定位微信进程

不同环境下微信进程名可能不同，例如 `WeChat`、`wechat`、`WeChatAppEx`、`wine` 或 Electron/容器包装进程。先用系统命令定位实际 PID：

```bash
pgrep -a -f 'WeChat|wechat|微信|wine'
```

也可以查看网络连接对应进程：

```bash
sudo ss -ntp | grep -Ei 'wechat|wine|WeChat'
```

拿到 PID 后，建议确认它的线程和命令行：

```bash
cat /proc/<PID>/comm
tr '\0' ' ' < /proc/<PID>/cmdline
ls /proc/<PID>/task | wc -l
```

如果微信由多个进程组成，需要分别观测每个关键进程，或者把采集程序扩展为按进程名自动刷新 PID。

## 构建和运行

准备环境参考仓库根目录 `README.md`。最小运行方式：

```bash
RUST_LOG=info cargo run --release -- --target-pid <微信PID>
```

程序启动后会：

1. 加载 eBPF object。
2. 初始化 eBPF logger。
3. 加载 CPU、IO、Network 相关 tracepoint/kprobe。
4. 启动 Prometheus exporter，监听 `0.0.0.0:9898`。
5. 等待 `Ctrl-C` 退出。

健康检查：

```bash
curl -s http://127.0.0.1:9898/health
```

指标输出：

```bash
curl -s http://127.0.0.1:9898/metrics
```

## 连接建立耗时观测

当前网络链路的核心观测点是：

```text
tcp_v4_connect -> sock:inet_sock_set_state
```

`tcp_v4_connect` 发生时，eBPF 程序把 socket 指针和当前时间写入 `START` map：

```text
key   = socket address
value = start timestamp ns
```

当 `inet_sock_set_state` 看到状态变化：

```text
old_state = TCP_SYN_SENT
new_state = TCP_ESTABLISHED
```

就用当前时间减去 `START` 中的开始时间，得到连接建立耗时。

日志形态类似：

```text
抓取到一个sock信息:<skaddr>
Socket:<skaddr> 旧状态:2 新状态:1 耗时为:<cost_ms>ms
```

解释：

- `旧状态:2` 表示 `TCP_SYN_SENT`。
- `新状态:1` 表示 `TCP_ESTABLISHED`。
- `耗时` 是从调用 `tcp_v4_connect` 到连接进入 established 的近似时间。

如果微信网络慢，可以重点观察：

- 单次连接建立耗时是否持续偏高。
- 是否出现大量发起连接但没有进入 established 的 socket。
- 是否和 DNS、代理、网络切换、防火墙策略有关。

## 发送方向观测

发送方向的 eBPF 程序中可以实现 `tcp_sendmsg` kprobe 逻辑。它可以读取：

- 当前进程 PID/TID。
- 地址族 IPv4/IPv6。
- 源 IP、源端口。
- 目标 IP、目标端口。
- 本次写入 TCP 协议栈的字节数 `size`。

日志形态类似：

```text
tcp_sendmsg pid=<pid> tid=<tid> family=ipv4 src=<src_ip>:<sport> dst=<dst_ip>:<dport> size=<bytes>
```

但当前 loader 中 `tcp_sendmsg` attach 还处于注释状态：

```rust
// KProberConfig::new("tcp_sendmsg", "tcp_sendmsg"),
KProberConfig::new("tcp_v4_connect", "tcp_v4_connect"),
```

如果要正式观测微信发送流量，需要把 `tcp_sendmsg` 加回 `kprobe_configs`：

```rust
let kprobe_configs = vec![
    KProberConfig::new("tcp_sendmsg", "tcp_sendmsg"),
    KProberConfig::new("tcp_v4_connect", "tcp_v4_connect"),
];
```

然后重新构建运行：

```bash
RUST_LOG=info cargo run --release -- --target-pid <微信PID>
```

验证时可以触发微信发送消息、打开图片、刷新会话或登录操作，观察是否出现 `tcp_sendmsg` 日志。

## Prometheus 指标

网络指标可以定义为：

```text
network_tcp_pid_total{pid="<pid>"} <count>
```

它的设计目标是统计进程级 TCP connect 次数。但当前 `sys_enter_connect` tracepoint 没有被 loader 加载，因此这个指标暂时不是完整可用状态。

要让该指标生效，需要在加载逻辑中恢复：

```rust
TracePointConfig::create_syscalls("sys_enter_connect", "sys_enter_connect"),
```

恢复后，`SYS_ENTER_CONNECT` map 会按 PID 累加 connect 调用次数，用户态 collector 再暴露到 `/metrics`。

建议后续指标拆分为：

```text
wechat_tcp_connect_total{pid}
wechat_tcp_connect_established_total{pid}
wechat_tcp_connect_latency_ms_bucket{pid}
wechat_tcp_send_bytes_total{pid, dst}
wechat_tcp_send_calls_total{pid, dst}
```

其中延迟直方图需要把 eBPF 侧事件传到用户态，或者在 eBPF map 中按桶聚合。

## 验证流程

建议按下面顺序验证，避免同时打开太多事件点导致排查困难。

### 1. 验证内核符号和 tracepoint

```bash
sudo bpftrace -l | grep '^kprobe:tcp_v4_connect$'
sudo bpftrace -l | grep '^kprobe:tcp_sendmsg$'
sudo bpftrace -l | grep '^tracepoint:sock:inet_sock_set_state$'
```

如果 `tcp_sendmsg` 查不到，可能是内核符号不可 kprobe、函数被优化、内核版本差异或权限限制。

### 2. 验证目标 PID

```bash
PID=$(pgrep -n -f 'WeChat|wechat|微信|wine')
echo "$PID"
cat /proc/$PID/comm
```

### 3. 运行采集程序

```bash
sudo RUST_LOG=info target/release/<采集程序> --target-pid "$PID"
```

或者：

```bash
sudo RUST_LOG=info cargo run --release -- --target-pid "$PID"
```

### 4. 触发微信网络行为

可选操作：

- 登录微信。
- 打开会话列表。
- 发送一条文本消息。
- 打开图片或文件。
- 进入小程序或公众号页面。

### 5. 观察日志和指标

```bash
curl -s http://127.0.0.1:9898/metrics
```

重点看：

- 是否能看到目标 PID 的 connect 事件。
- 是否能看到连接建立耗时日志。
- 如果启用了 `tcp_sendmsg`，是否能看到目标地址和发送字节数。

## 故障排查

### 没有任何网络日志

检查：

- 是否使用 `sudo` 运行。
- `--target-pid` 是否是实际发起网络请求的微信进程。
- 微信是否存在多进程，需要换 PID。
- 当前 loader 是否真的 attach 了目标 kprobe。
- 内核是否允许挂载对应 kprobe。

### 有 connect 但没有 established

可能原因：

- 连接失败。
- 目标网络不可达。
- 代理、VPN、防火墙或 DNS 异常。
- socket 指针没有正确关联到 `START` map。

可以补充观测 `sys_exit_connect` 返回值，确认 connect 是否返回错误码。

### 有连接但没有发送日志

检查：

- `tcp_sendmsg` 是否已经在 loader 中打开。
- 微信是否使用了其他进程发送数据。
- 发送动作是否真的触发 TCP 写入。
- 是否存在 UDP/QUIC 路径，当前 `tcp_sendmsg` 不覆盖 UDP。

## 后续开发建议

建议按下面顺序推进：

1. 恢复 `tcp_sendmsg` attach，并验证按 `--target-pid` 过滤发送日志。
2. 恢复 `sys_enter_connect` tracepoint，让 `network_tcp_pid_total` 指标真实可用。
3. 增加按进程名过滤能力，例如 `--target-comm WeChat`，并周期刷新 PID。
4. 增加连接维度 map，按 `pid + dst_ip + dst_port` 聚合发送字节数。
5. 增加 connect 成功、失败、耗时分桶指标。
6. 增加 UDP/QUIC 观测点，例如 `udp_sendmsg` 或相关 tracepoint。
7. 把日志型观测沉淀为 Prometheus 指标，减少线上排查时的日志噪声。

## 边界和合规

本项目应只做系统性能和网络元数据观测，不读取、不记录、不输出微信消息内容、联系人、文件内容、密钥、cookie、token 或 TLS 明文。涉及个人通信数据时，应只在授权环境中进行排查，并控制日志留存范围。
